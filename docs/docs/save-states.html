Save States

4 numbered slots per game, alongside your normal in-game saves. The scope is deliberately narrow — read this before you rely on it.

On this page

  • The real limit
  • Where they live
  • What's captured
  • Around the save/load call

The real limit: same running instance only

Read this first

A save only loads back into the exact same running game instance it was taken from. Quitting or relaunching the game — or restarting the app — breaks the match, and a save from before that point will always fail to load.

Loading is refused outright, with no memory touched, unless the currently running title's ID, active thread list, and mapped memory layout all match the save exactly. That is expected behaviour, not a bug: there is no safe way to reconcile a save against a session it does not line up with.

In practice, save states are a same-session "checkpoint before a hard section", not a way to resume a game across app launches. Your normal in-game saves are still what carries progress between sessions.

Where they live

Each game gets its own folder: Documents/SaveStates/<game.id>/, with up to 4 files named slot1.sav through slot4.sav. That is namespaced by the game's own id — its ROM/dump filename — rather than its Wii U title ID, because a homebrew build or an unrecognised dump can lack a title ID entirely. Using the always-present id means those never collide with each other's slots.

Open the sheet from the in-game top bar. Each slot shows empty, or "Saved <relative time>", with Save/Overwrite, Load, and Delete actions.

What's actually captured

A save state freezes the running title's guest RAM — every currently-mapped memory region, raw bytes — to the slot file. That is it. Deliberately, it does not capture:

  • GPU/renderer state — no textures, shaders, vertex or uniform buffer caches
  • CPU registers as a separate blob

CPU state is not missing, though. Cafe OS already keeps every thread's register context inside guest memory itself (OSThread_t.context) whenever that thread is not the one actively mid-timeslice on a core. Once every core has reached its idle fiber — confirmed before the save runs — a plain RAM dump already contains complete, correct register state for every thread, restored for free through the same code path a normal thread switch already uses.

Why GPU state is left alone

Cemu's GX2/Latte layer already treats VRAM-side objects as caches derived from guest memory, invalidated by explicit signals from the game itself. A RAM-only load bypasses those signals, so a texture or shader could briefly show its pre-save contents until the game's own next GX2 call refreshes it.

That is the one accepted trade-off of this design: a brief visual glitch, not lost data or a correctness problem. The alternative — force-invalidating every GPU cache from outside the GPU thread while it is still running — was judged an untested, unsafe cross-thread path and deliberately not attempted.

Around the save/load call

Saving pauses the title if it is not already paused, waits for every CPU core to genuinely reach idle — not just "asked to pause", since a core mid-timeslice can keep writing to guest memory for a full quantum otherwise — writes the file, then resumes if this call was the one that paused it.

It fails cleanly, with no partial file, if no title is running, a core never quiesces within a few seconds, or the write itself fails. A successful load also forces the recompiler to drop any JIT-compiled code that may now be stale, which is a safe no-op under the interpreter.
